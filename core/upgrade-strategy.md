# 升级策略

要升级插件，最关键的一个步骤就是将插件的新版本 JAR 文件替换掉旧的文件，使服务端加载这个新的文件，从而达到升级的目的。替换文件的方式有很多种，您可以先删除文件，再复制新的文件，也可以直接用同名文件进行覆盖，UPU 的升级策略本质上就是不同的文件复制方式，而不同的升级策略在不同的系统和平台均有不同的行为，本页面描述 UPU 内置的一些升级策略，以及如何创建一个新的升级策略。

## 关于文件系统

在描述 UPU 的升级策略之前，让我们先来了解一下操作系统组织文件的方式，这有助于您了解 UPU 的升级策略的工作方式。

每个插件都是一个 JAR 文件，这个文件存放在您的服务器上的一个叫[文件系统](https://www.qiuwenbaike.cn/wiki/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F)的东西，您不太需要关注文件系统本身，只需要知道不同的操作系统通常使用不同的文件系统，并且这些文件系统的行为是不一样的。

在 Windows 系统中，最常见的文件系统是 [NTFS](https://www.qiuwenbaike.cn/wiki/NTFS)，其设计围绕一个核心展开：**一切文件与目录，本质上都是主文件表（MFT）中的一条“记录”**。对文件所做的操作本质上是对这条记录进行操作，而在 Windows 上访问文件实际上是申请“权限”的过程，当服务端进程想要读取插件文件时，它会向操作系统申请两个权限，第一个是“我想做什么”，第二个是“在我做的适合其他人能做什么”，前者向操作系统申请操作文件的权限，后者向操作系统声明应当拒绝其他进程申请什么权限。服务端进程通常会告诉操作系统：“你不能允许其他进程在我读取这个文件的适合删除这个文件！”，这样，当我们尝试在 Windows 操作系统上删除一个已被加载的插件文件，就会出现“另一个进程正在使用此文件，进程无法访问”的错误提示框。

在 Linux 系统（以及整个 Unix 世界）中，情况略有不同，**所有文件都分为两个独立的部分：索引节点和目录项**。索引节点也称为 [inode](https://www.qiuwenbaike.cn/wiki/Inode)，是文件的真正实体，它存储了文件的所有元数据（权限、大小、时间戳等）以及数据块在磁盘上的位置，每个 inode 有一个唯一的编号。目录项则仅仅是一个“名称标签”，每个目录都对应一个“目录文件”，目录文件中保存了一张映射表，将人类可读的文件名与一个 inode 编号关联起来。这个“名称 → inode编号”的链接，就是硬链接。一个 inode 可以同时被多个目录项（即多个不同的文件名，甚至在不同目录下）所指向，文件名只是访问 inode 的路径之一，而非 inode 本身。因此，在 Linux 上删除文件本质上是删除硬链接，并使这个硬链接对应的 inode 的链接计数减 1。这个过程完全不关心是否有进程正在打开这个 inode，因为删除一个硬链接并不影响其他的硬链接，只有当没有任何进程和任何目录项对应这个文件时，这个文件才会在文件系统中被真正删除。这种设计带来了一些 Windows 上难以实现的优雅能力，您有时会注意到，即便您在 Linux 上的服务端进程仍在运行，您也可以删除这个服务端进程占用的插件并以新插件替换。

## UPU 内置的升级策略

现在，我们将刚刚介绍的关于文件系统的知识和 UPU 内置的几个升级策略放在一起解释，帮助您更好的了解这些升级策略并选择一个最佳的策略。每个策略的 ID 都以小标题的形式展示，您可以直接在配置文件中使用对应的策略 ID。

### `native`

- 可用平台：全部

这个策略意思是“原生”升级策略，意味着其使用操作系统提供的文件操作能力对插件文件进行升级操作。在执行升级操作时，此策略会首先尝试卸载插件并关闭服务端进程对插件文件的引用，目的是为了解除文件占用。然后删除旧的插件文件，并将已提前下载好的新插件文件放在插件文件夹中。这一切完成后，您只需要重启服务端即可使用新的插件完成升级过程。

您可能会觉得这个策略与您手动替换文件没有任何区别，事实也是如此，因此这个策略也会受到不同的操作系统和服务端的限制。以 Windows 上的 Velocity 服务端为例，Windows 不支持在文件占用时删除文件，而 Velocity 不支持在运行中卸载插件从而解除文件占用，因此，在 Windows 上的 Velocity 服务端使用 native 策略是无法正常工作的。但如果您使用的不是 Velocity 服务端或者使用的是 Linux 系统，那么 native 策略应该能够正常工作，因为 Bukkit 和 BungeeCord 支持运行时卸载插件并解除文件占用，而 Linux 支持文件被占用时对文件进行操作。

由于显而易见的原因，如果使用此策略，UPU 通常只会在服务端将要关闭的插件卸载阶段执行升级操作，以将此策略造成的副作用降至最低。您可以使用 `--now` 参数让 UPU 在运行时升级插件，但 native 策略的卸载插件操作会让被升级的插件在服务端重启之前不可使用，从而可能对您的服务器造成不良影响，尤其是被升级的插件属于保护类型的插件时，插件提供的保护功能会完全失效。

### `applier`

- 可用平台：全部

这个策略是 native 策略的一个变通方案，区别在于此策略会启动一个新进程，并由这个新进程完成插件文件的替换操作。（假设）既然我们无法在进程运行时对文件进行操作，那么为什么我们不在服务端将要关闭时启动一个新的进程，让这个进程在服务端进程结束后进行文件替换操作呢？这就是 applier 策略的设计思路，用新进程来避免文件被占用的问题。

这个策略使 Windows 上的 Velocity 服务端自动升级插件成为可能，我们不用在乎操作系统和服务端的限制，因为这些限制变得可以被避免，新的进程会在一段时间内等待，直到文件不再被占用，然后立刻使用新的插件文件替换旧的文件。当然，对于一些不支持创建新进程的环境，此策略可能无法正常工作，Docker 容器就是这样一种场景，不过考虑到 Docker 容器大多是 Linux 系统，您可能会想直接使用 native 策略。

由于要启动新进程，并且设计上是 native 策略的改良版，如果使用此策略，UPU 也只会在服务端将要关闭的插件卸载阶段执行升级操作。

### `bukkit`

- 可用平台：Bukkit

与之前提到的两个策略不同，bukkit 策略顾名思义只能在 Bukkit 上使用，这个策略利用了 Bukkit 的一个名为[更新文件夹](https://docs.papermc.io/paper/updating/#step-2-update-plugins)的功能，在服务端启动后、插件加载前用新插件文件替换旧的插件文件，这一机制在 Paper 上其更加完善。

这个策略会通过 Bukkit API 的 `getUpdateFolder()` 获取更新文件夹的路径，然后将先前下载的新版本的插件文件放在这个文件夹，升级就算完成，下次启动服务端时，Bukkit 会完成替换文件的操作并加载新的插件文件。由于 UPU 不必直接操作文件，因此此策略相比之前提到的两个策略都更加安全，但同时 UPU 也无法在其他服务端上提供这个策略。或许其他服务端日后也会有类似特性，不过到那时 UPU 可能会以服务端的名称命名对应的策略。

需要注意的是，此策略在不同版本的 Bukkit 和 Paper 的行为不一致。至少到 1.16.5 的 Bukkit，这个机制只会替换插件文件夹中的同名插件，如果插件的旧版本的文件名为 `MyPlugin-1.0.jar`，而新版本的文件名为 `MyPlugin-1.1.jar`，那么 Bukkit 并不会进行文件操作。Paper 对此机制进行了优化，无论文件名如何，只要文件对应的插件是同一个就会进行替换。因此，如果您不使用 Paper，则可能还需要调整配置文件的 [`updater.filename`](/core/config/config.yml#updater-filename) 配置项来指定 UPU 下载插件文件时使用的文件名。

如果使用此策略，UPU 会在任何时间执行升级操作，因为此策略的升级操作是安全的，实际的升级行为由 Bukkit 控制。

## 创建新的升级策略

如果您有一个升级策略的好思路，您可以帮助 UPU 支持更多的升级策略。如果您拥有一些 Java 开发基础，还可以使用代码让您的想法变成 UPU 的一部分。我们将在这个部分描述如何以开发者的身份创建一个新的升级策略，并使 UPU 能够使用。

需要注意的是，创建一个新插件并声明依赖 UPU 来提供升级策略并不是一个好主意，因为升级策略的代码必须在 UPU 被卸载时保持可用，而一个插件的附属插件通常都先于自身卸载，因此除非您可以控制插件的卸载顺序（这通常做不到），将升级策略内置进 UPU 是一个更好的选择。

在 `me.dreamvoid.universalpluginupdater.upgrade` 包中，您可以看到 UPU 的升级策略接口 `UpgradeStrategy` 和已实现的两个升级策略 `NativeUpgradeStrategy` 和 `ApplierUpgradeStrategy`。要创建您的升级策略，只需要在这个包中新建一个实现 `UpgradeStrategy` 的类，在这里，我们假设其名为 `MyUpgradeStrategy`。在这个类中实现必要的接口即可，就像下面这样：

```java
package me.dreamvoid.universalpluginupdater.upgrade;

import org.jetbrains.annotations.NotNull;

import java.util.List;

/**
 * @author Me
 */
public class MyUpgradeStrategy implements UpgradeStrategy{
    @NotNull
    @Override
    public String getId() {
        return "mystrategy";
    }

    @NotNull
    @Override
    public List<UpgradeResult> upgrade(@NotNull List<UpgradeTask> tasks) {
        // Do upgrade
        return List.of();
    }
}
```

只有两个方法是必须的：`getId()` 方法用于声明这个策略的标识符，供用户在配置文件中指定；`upgrade(List)` 方法用于执行实际的升级操作，形参 `tasks` 代表本次升级操作的所有需要升级的插件的信息，包括插件 ID、新版本文件的位置，旧版本文件的位置（如有）。您可以自由发挥，只需要为每个插件的升级结果提供一个 `UpgradeResult` 对象，并将本次任务中所有插件的升级结果组合成一个 `List` 对象返回即可。如果单个插件的升级操作出现了异常，应当在 `upgrade` 方法内部进行处理，如果 `upgrade` 方法抛出了异常，UPU 会认为是升级策略本身出了问题，并认为所有插件都升级失败了。

您还可以实现默认返回 `null` 的 `getName()` 方法，为您的升级策略取一个好看的名字。如果您的策略足够安全，能够随时随地进行升级操作，则还可以重写 `getExecutionPhase()` 方法，返回 `ExecutionPhase.RUNTIME` 让 UPU 知道您的策略可以随时随地进行升级而不必担心出现任何问题。

实现完成后，您就可以向 UPU 注册升级策略，在 `LifeCycle` 类的 `preLoad` 方法中，约 70 行左右的位置您可以找到现有的几个策略的注册位置：

```java
UpgradeStrategyRegistry.instance().registerStrategy(new NativeUpgradeStrategy(platform));
UpgradeStrategyRegistry.instance().registerStrategy(new ApplierUpgradeStrategy(platform));
```

将您的策略实例化后使用 `registerStrategy` 注册即可。
